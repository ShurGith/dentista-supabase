Actúa como un equipo senior de bases de datos PostgreSQL, seguridad, arquitectura de software, DevOps, backend Node.js/TypeScript y desarrollo full-stack.

Vas a crear, revisar, completar e integrar la base de datos de Supabase, el almacenamiento de archivos y el despliegue de una aplicación de gestión de citas para una clínica odontológica.

La aplicación ya dispone de:
- Frontend web en React + Vite + TypeScript + Tailwind CSS + shadcn/ui.
- App móvil en React Native con Expo.
- Backend en Node.js con TypeScript.
- Supabase como base de datos, autenticación, Storage, Realtime y Row Level Security.
- Panel de administración tipo CRM.
- Calendario de citas con arrastrar, soltar y redimensionar.
- Gestión de pacientes, profesionales, servicios, horarios, usuarios, roles y permisos.
- Web pública de la clínica.
- Integración con Wawp para WhatsApp.
- Modales de aviso de error y modales para todos los avisos que sean necesarios.

OBJETIVO PRINCIPAL

Crear una base de datos Supabase completa, segura, escalable y lista para producción.

Debes generar:
1. Los scripts SQL completos para crear todas las tablas.
2. Las políticas RLS completas para cada tabla.
3. La configuración completa de Supabase Storage.
4. Las migraciones versionadas.
5. Los índices, funciones, triggers, vistas y seed necesarios.
6. Los tests de RLS y seguridad.
7. El plan de integración con el backend, frontend y app móvil.
8. El plan completo de despliegue a producción.

La base de datos no debe tener errores, advertencias ni incidencias de seguridad en el Security Advisor, el linter de Supabase o los tests de RLS.

No modifiques ni elimines funcionalidades existentes salvo que sea necesario para corregir problemas de seguridad, integridad, rendimiento o despliegue.

REGLA CRÍTICA DE SEGURIDAD

No entregues una base de datos con:
- Tablas expuestas sin RLS habilitado.
- Políticas RLS ausentes, incompletas o permisivas.
- Políticas `USING (true)` o `WITH CHECK (true)` sin justificación explícita.
- Acceso cruzado entre clínicas.
- Acceso no autorizado a datos clínicos, documentos, WhatsApp, usuarios, roles, configuración o auditoría.
- Secretos, tokens, API keys o credenciales expuestos.
- Permisos excesivos para `anon` o `authenticated`.
- Funciones inseguras.
- Vistas inseguras.
- Buckets de Storage públicos que contengan datos sensibles.
- Fallos en `supabase db lint`, `supabase db advisors` o `supabase test db`.

Supabase advierte que una tabla expuesta sin RLS puede ser leída o modificada por cualquier rol con permisos, y que políticas como `USING (true)` anulan la protección. [27][28]

ALCANCE EXCLUIDO

No incluyas pagos online, prepago, cobros, pasarelas de pago, suscripciones, facturación, presupuestos económicos, precios, importes, descuentos, cupones, carritos, pedidos, reembolsos, recordatorios de pago ni ninguna funcionalidad relacionada con transacciones económicas.

La aplicación se limita exclusivamente a la gestión de citas, pacientes, profesionales, comunicación por WhatsApp y administración de la clínica.

STACK Y CONTEXTO

- Frontend web: React + Vite + TypeScript + Tailwind CSS + shadcn/ui.
- App móvil: React Native con Expo.

PARTE 1 — ARQUITECTURA DE LA BASE DE DATOS

Crea la base de datos en el esquema `public`.

Usa una arquitectura multi-clínica desde el inicio.

Toda tabla que contenga datos de una clínica debe incluir `clinic_id`.

No permitas que un usuario acceda a datos de una clínica a la que no pertenece.

Usa UUID como clave primaria en todas las tablas.

Usa `timestamptz` para todas las fechas y horas.

Usa enums de PostgreSQL para estados y tipos controlados.

Usa soft delete cuando proceda.

Incluye `created_at`, `updated_at`, `created_by` y `updated_by` cuando proceda.

PARTE 2 — SCRIPTS SQL COMPLETOS PARA CREAR LAS TABLAS

Genera migraciones SQL completas, ejecutables y versionadas para crear toda la base de datos.

No entregues pseudocódigo ni fragmentos incompletos.

Cada migración debe poder ejecutarse de forma segura en una base de datos vacía.

4.1 Función auxiliar para obtener la clínica del usuario

create or replace function public.current_user_clinic_id()
returns uuid
language sql
stable
security invoker
set search_path = public
as $$
  select clinic_id
  from public.profiles
  where id = auth.uid()
  limit 1;
$$;

No uses  security definer  salvo que sea imprescindible.
Si usas  security definer , fija siempre  search_path  y concede únicamente los permisos mínimos.

7.3 Políticas RLS de Storage
Crea políticas RLS sobre  storage.objects  para cada bucket y operación.
Supabase indica que, por defecto, Storage no permite subidas sin políticas RLS y que las políticas deben crearse sobre  storage.objects  para  SELECT ,  INSERT ,  UPDATE  y  DELETE . 
Ejemplo para documentos privados de pacientes:
create policy "Authenticated clinic users can read patient documents"
on storage.objects
for select
to authenticated
using (
  bucket_id = 'patient-documents'
  and exists (
    select 1
    from public.patient_documents pd
    join public.profiles p on p.clinic_id = pd.clinic_id
    where pd.storage_path = name
      and p.id = auth.uid()
  )
);

create policy "Authorized clinic users can upload patient documents"
on storage.objects
for insert
to authenticated
with check (
  bucket_id = 'patient-documents'
  and exists (
    select 1
    from public.profiles p
    where p.id = auth.uid()
      and exists (
        select 1
        from public.user_roles ur
        join public.roles r on r.id = ur.role_id
        join public.role_permissions rp on rp.role_id = r.id
        join public.permissions perm on perm.id = rp.permission_id
        where ur.user_id = auth.uid()
          and perm.slug = 'patients.manage_documents'
      )
  )
);

No copies estas políticas sin adaptarlas a la estructura real de rutas, metadatos y permisos del proyecto.

## Nota sobre RLS

Supabase recomienda crear una política por operación —`SELECT`, `INSERT`, `UPDATE` y `DELETE`—, especificar siempre el rol con `TO`, usar `WITH CHECK` en inserciones y actualizaciones, y añadir índices a las columnas usadas por las políticas. También recomienda revocar grants por defecto y conceder solo los privilegios necesarios.[1]

## Nota sobre Storage

Las políticas de Storage deben crearse sobre `storage.objects`, especificando bucket, rol y operación. Supabase permite restringir por `bucket_id` y carpeta, y recomienda usar URLs firmadas para archivos privados.[2]

## Nota sobre despliegue

El flujo recomendado es crear migraciones locales, validarlas con `supabase db reset`, ejecutar linting y tests, vincular el proyecto con `supabase link` y aplicar las migraciones con `supabase db push --remote`. Supabase también permite incluir el seed durante el despliegue con `--include-seed`.
