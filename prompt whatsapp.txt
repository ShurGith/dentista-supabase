Actúa como un equipo senior de backend Node.js/TypeScript, arquitectura de software, integraciones de APIs, seguridad y producto.

Vas a realizar un conjunto de retoques y ajustes sobre una aplicación existente de gestión de citas para una clínica odontológica.

La aplicación ya dispone de:
- Frontend web en React + Vite + TypeScript + Tailwind CSS + shadcn/ui.
- App móvil en React Native con Expo.
- Backend en Node.js con TypeScript.
- Supabase como base de datos, autenticación, Storage y Row Level Security.
- Panel de administración tipo CRM.
- Calendario de citas con arrastrar, soltar y redimensionar.
- Gestión de pacientes, profesionales, servicios, horarios, usuarios, roles y permisos.
- Web pública de la clínica.
- Integración base con Wawp para WhatsApp.

No modifiques ni elimines funcionalidades existentes salvo que sea necesario para implementar correctamente los cambios solicitados.

OBJETIVO DE ESTE RETOQUE

Centralizar toda la gestión de WhatsApp en el backend, mejorar la integración con Wawp, añadir plantillas editables desde el panel de administración y automatizar los mensajes relacionados con el ciclo de vida de una cita.

La gestión de WhatsApp debe realizarse desde el propio backend. El frontend nunca debe contener credenciales, tokens, secretos ni realizar llamadas directas a la API de Wawp.

1. CONFIGURACIÓN DE WAWP EN EL BACKEND

Añade o actualiza la configuración de Wawp en el archivo `.env.example` y en la configuración del backend.

Utiliza estas variables de entorno, con estos nombres exactos:

WAWP_DRIVER=api
WAWP_BASE_URL=https://api.wawp.net
WAWP_ACCESS_TOKEN=wawp_access_token
WAWP_INSTANCE_ID=WAWP_INSTANCE_ID
WAWP_APP_TIMEZONE=Europe/Madrid
WAWP_TUNNEL_URL=https://UN_TUNEL_GROK.ngrok-free.dev/api/wawp/webhook?secret=un-secreto
WAWP_WEBHOOK_SECRET=un-secreto

Requisitos:

- Crea un módulo de configuración centralizado para cargar y validar estas variables al arrancar el backend.
- Valida que las variables obligatorias existan y tengan un formato razonable.
- No incluyas valores reales de tokens, secretos ni identificadores en el repositorio.
- Añade un archivo `.env.example` con las variables anteriores y valores de ejemplo claramente identificables como ficticios.
- Añade `.env` al `.gitignore` si aún no lo está.
- Usa `WAWP_APP_TIMEZONE` para programar recordatorios, calcular horas locales y formatear fechas en los mensajes.
- Usa `WAWP_TUNNEL_URL` solo como URL pública del webhook durante desarrollo local.
- Usa `WAWP_WEBHOOK_SECRET` para validar la autenticidad de las peticiones entrantes del webhook.
- Crea un adaptador o servicio `WawpService` que encapsule toda la comunicación con la API de Wawp.
- El resto del backend no debe conocer detalles internos de Wawp; debe depender de una interfaz como `WhatsAppProvider`.
- Deja preparada la posibilidad de cambiar de proveedor en el futuro mediante el valor de `WAWP_DRIVER`.
- Implementa logging estructurado para envíos, respuestas, errores, reintentos y eventos de webhook.
- No registres el contenido completo de mensajes ni datos personales sensibles en los logs por defecto.
- Implementa reintentos con backoff exponencial para errores temporales de red o de la API.
- Implementa idempotencia para evitar enviar el mismo mensaje dos veces.

4. PLANTILLAS INICIALES OBLIGATORIAS

Crea estas cuatro plantillas iniciales y déjalas disponibles en el seed inicial de la base de datos.

4.1 Plantilla de recordatorio de cita

Nombre interno:
`appointment_reminder`

Propósito:
Enviar un recordatorio automático antes de una cita.

Debe incluir tres botones:

1. Botón de confirmación de cita.
- Texto configurable, por ejemplo: “Confirmar cita”.
- Acción: confirmar la cita.
- Debe actualizar el estado de la cita a confirmada.
- Debe registrar la acción en el historial de la cita.
- Debe notificar al panel mediante Supabase Realtime si está implementado.

2. Botón de solicitud de cambio de cita.
- Texto configurable, por ejemplo: “Cambiar cita”.
- Acción: solicitar cambio de cita.
- Debe abrir un flujo para que el paciente solicite una nueva fecha y hora.
- Debe crear una solicitud de reprogramación pendiente.
- Debe enviar automáticamente la plantilla de cambio de cita.

3. Botón de anulación de cita.
- Texto configurable, por ejemplo: “Anular cita”.
- Acción: anular la cita.
- Debe solicitar confirmación antes de cancelar la cita.
- Debe actualizar el estado de la cita a cancelada por paciente.
- Debe enviar automáticamente la plantilla informativa de anulación.

El texto base de la plantilla debe poder incluir, por ejemplo:
“Hola {{patient_first_name}}, te recordamos tu cita en {{clinic_name}} el {{appointment_date}} a las {{appointment_time}} con {{professional_name}} para {{service_name}}. ¿Confirmas tu asistencia?”

4.2 Plantilla de confirmación de cita creada

Nombre interno:
`appointment_created_confirmation`

Propósito:
Enviar automáticamente cuando se crea una nueva cita.

Debe incluir los mismos tres botones que la plantilla de recordatorio:

1. Confirmar cita.
2. Cambiar cita.
3. Anular cita.

El texto base debe poder incluir, por ejemplo:
“Hola {{patient_first_name}}, tu cita en {{clinic_name}} ha sido creada para el {{appointment_date}} a las {{appointment_time}} con {{professional_name}} para {{service_name}}. ¿Confirmas tu asistencia?”

4.3 Plantilla de cambio de cita

Nombre interno:
`appointment_reschedule_requested`

Propósito:
Enviar automáticamente cuando el paciente solicita un cambio de cita.

No debe incluir botones.

El texto base debe poder incluir, por ejemplo:
“Hola {{patient_first_name}}, hemos recibido tu solicitud para cambiar tu cita del {{appointment_date}} a las {{appointment_time}}. Nuestro equipo se pondrá en contacto contigo para proponer una nueva fecha y hora. Gracias por tu paciencia.”

4.4 Plantilla informativa de anulación

Nombre interno:
`appointment_cancelled_confirmation`

Propósito:
Enviar automáticamente cuando el paciente anula una cita.

No debe incluir botones.

El texto base debe poder incluir, por ejemplo:
“Hola {{patient_first_name}}, tu cita del {{appointment_date}} a las {{appointment_time}} en {{clinic_name}} ha sido anulada correctamente. Si deseas reservar una nueva cita, estaremos encantados de atenderte.”

5. GESTIÓN DE BOTONES EN LAS PLANTILLAS

El panel debe permitir configurar botones por plantilla.

Para cada botón, el administrador debe poder definir:
- Texto visible del botón.
- Orden del botón.
- Estado activo o inactivo.
- Tipo de acción.
- Acción asociada.
- URL o endpoint de destino, si aplica.
- Mensaje automático que se enviará tras la acción, si aplica.

Tipos de acción soportados:
- Confirmar cita.
- Solicitar cambio de cita.
- Anular cita.
- Abrir enlace externo.
- Abrir la app móvil.
- Abrir una página web.
- Enviar una respuesta predefinida por WhatsApp.

Reglas:
- Una plantilla puede tener cero, uno, dos o tres botones.
- El número máximo de botones debe respetar las limitaciones reales de la API o del tipo de mensaje utilizado por Wawp.
- Si la API no permite tres botones interactivos en un mismo mensaje, implementa una alternativa segura, por ejemplo botones de respuesta rápida, enlaces firmados o un menú de opciones.
- Los botones deben generar enlaces únicos, firmados y con expiración para confirmar, reprogramar o cancelar.
- Los enlaces deben incluir un token seguro, el identificador de la cita y una fecha de expiración.
- No permitas que un enlace pueda reutilizarse después de que la cita haya cambiado de estado.
- Registra cada pulsación de botón, la acción realizada, el usuario o paciente asociado, la fecha y el resultado.

6. AUTOMATIZACIONES DE WHATSAPP

Implementa los siguientes flujos automáticos desde el backend.

6.1 Confirmación al crear una cita
- Cuando se crea una cita, el backend debe enviar automáticamente la plantilla `appointment_created_confirmation`.
- La plantilla debe incluir los tres botones: confirmar, cambiar y anular.
- El envío debe registrarse en `message_logs`.
- Si el envío falla, debe quedar registrado como fallido y poder reintentarse.
- El administrador debe poder activar o desactivar este envío automático desde la configuración.

6.2 Recordatorio antes de la cita
- Crea un job programado que revise periódicamente las citas próximas.
- El job debe enviar la plantilla `appointment_reminder` según la configuración de la clínica.
- Permite configurar varios recordatorios, por ejemplo 24 horas antes y 2 horas antes.
- Evita duplicados mediante un identificador único por cita, plantilla y envío programado.
- Respeta la zona horaria definida en `WAWP_APP_TIMEZONE`.
- Si el paciente ya confirmó, canceló o solicitó un cambio, no envíes recordatorios innecesarios.
- Si el envío falla, reintenta con backoff y registra el error.
- El administrador debe poder activar o desactivar los recordatorios y modificar los intervalos.

6.3 Cambio de cita solicitado
- Cuando el paciente pulsa “Cambiar cita”, el backend debe:
  - Crear una solicitud de reprogramación pendiente.
  - Actualizar el estado de la cita a “en espera” o a un estado equivalente.
  - Enviar automáticamente la plantilla `appointment_reschedule_requested`.
  - Notificar al personal autorizado en el panel.
  - Registrar la acción y el mensaje enviado.

6.4 Anulación de cita
- Cuando el paciente pulsa “Anular cita”, el backend debe:
  - Solicitar confirmación explícita antes de anular.
  - Actualizar el estado de la cita a “cancelada por paciente”.
  - Enviar automáticamente la plantilla `appointment_cancelled_confirmation`.
  - Notificar al personal autorizado en el panel.
  - Registrar la acción y el mensaje enviado.

6.5 Reprogramación confirmada
- Cuando recepción o un dentista reprograma una cita desde el calendario, el backend debe poder enviar un aviso automático al paciente.
- El aviso debe usar una plantilla editable.
- El administrador debe poder activar o desactivar este aviso.

7. WEBHOOK DE WAWP

Crea un endpoint seguro para recibir eventos de Wawp:

`POST /api/wawp/webhook`

Requisitos:
- Valida el secreto recibido mediante `WAWP_WEBHOOK_SECRET`.
- Rechaza peticiones sin firma, token o secreto válido.
- Implementa idempotencia para evitar procesar el mismo evento dos veces.
- Guarda cada evento recibido en `webhook_events`.
- Procesa los eventos de forma asíncrona cuando sea posible.
- Actualiza el estado de los mensajes enviados: enviado, entregado, leído o fallido.
- Guarda los mensajes entrantes en `whatsapp_messages`.
- Asocia cada mensaje entrante al paciente mediante el número de teléfono.
- Si no existe el paciente, crea un contacto pendiente de revisión o lo asocia a un paciente existente según la configuración.
- Actualiza la conversación correspondiente en `whatsapp_conversations`.
- Actualiza el estado de una cita cuando el paciente confirma, solicita cambio o anula mediante un botón o enlace.
- Notifica al panel en tiempo real mediante Supabase Realtime, si está disponible.
- Registra errores sin interrumpir el procesamiento del resto de eventos.
- Devuelve una respuesta rápida al webhook para evitar timeouts.
- No expongas información sensible en los logs ni en las respuestas de error.

11. SEGURIDAD

- Nunca almacenes ni expongas `WAWP_ACCESS_TOKEN`, `WAWP_INSTANCE_ID` ni `WAWP_WEBHOOK_SECRET` en el frontend.
- Nunca incluyas estos valores en respuestas de API, logs, mensajes de error o repositorio.
- Valida todas las peticiones del webhook mediante el secreto configurado.
- Usa HTTPS obligatorio en producción.
- Implementa rate limiting en los endpoints de envío y webhook.
- Implementa idempotencia en todos los envíos y webhooks.
- Valida que el paciente tenga permiso para realizar la acción asociada a un botón o enlace.
- Expira los enlaces de confirmación, cambio y anulación.
- Registra todos los accesos y acciones relacionadas con WhatsApp en `audit_logs`.
- Cumple RGPD: minimización de datos, consentimiento, derecho de acceso, rectificación, supresión y registro de comunicaciones.
- No envíes mensajes masivos sin control, límites y registro.
- Usa un número de prueba de Wawp durante el desarrollo para evitar restricciones o bloqueos de WhatsApp.
- Los enlaces de los botones deben usar tokens únicos, firmados y con caducidad. Así, aunque alguien reenvíe o manipule un enlace, no podrá confirmar, cambiar ni anular una cita ajena ni reutilizar una acción ya ejecutada.
